1. Contexte
Vous êtes Data Engineer dans
Maelys Marketplace
, une marketplace e-commerce française qui met en relation des vendeurs indépendants (artisans, marques DNVB, revendeurs) et des consommateurs finaux. Maelys prend une commission de 12% sur chaque vente.
Chiffres (fictifs) :
2 400 vendeurs actifs · 180 000 produits · ~8 500 commandes/jour
CA mensuel ~4.2 M€
75 personnes en interne dont 1 analyste qui passe
2 jours par semaine
à extraire à la main les données du backoffice pour produire des rapports Excel
Le besoin
Le
CEO
veut un dashboard hebdomadaire avec les KPIs clés (top vendeurs, CA par catégorie, panier moyen). L'
équipe finance
a besoin de données fiables pour la clôture mensuelle et la facturation des commissions. Le
responsable catalogue
veut détecter les anomalies (drop de ventes, prix suspects).
Aujourd'hui :
tout est manuel
, les rapports sont en retard, les erreurs de copier-coller sont fréquentes, et l'analyste passe 40% de son temps sur de l'extraction au lieu de faire de l'analyse.
Votre mission
Construire en 2 jours un
MVP de plateforme data
qui :
Ingère automatiquement les données depuis l'API du backoffice
Les stocke dans un Data Warehouse propre (modélisation dimensionnelle)
Expose des KPIs lisibles via un outil BI (Metabase)
Détecte les anomalies commerciales basiques
Vous êtes l'équipe Data nouvellement recrutée. Aucune infrastructure data n'existe — vous partez de zéro. Le code doit être maintenable, testé, et reproductible (Docker Compose).

3.2 Flux d'un pipeline run
sequenceDiagram
participant S as Scheduler
participant H as MarketplaceAPIHook
participant A as API Marketplace
participant M as MinIO
participant P as PostgreSQL
participant MB as Metabase
S->>H: declenche extract (date={{ ds }})
H->>A: GET /orders?date=...
A-->>H: JSON N commandes
H->>M: PUT raw/orders/dt=.../data.json
H->>P: INSERT staging.orders (idempotent)
S->>P: DELETE + INSERT dwh.fact_orders WHERE dt = ...
S->>P: REFRESH analytics.daily_summary
MB->>P: SELECT pour le dashboard
3.3 Pourquoi cette architecture
MinIO comme raw layer
: conserver le JSON brut en archive permet de
rejouer
un pipeline si la transformation a un bug, sans devoir re-appeler l'API source. C'est le pattern "data lake first".
3 schémas PostgreSQL séparés
:
staging
(données brutes typées),
dwh
(modèle dimensionnel propre),
analytics
(agrégations pré-calculées pour les dashboards). C'est plus propre qu'un seul schéma fourre-tout.
Metabase plutôt que Superset
: plus simple à mettre en place, suffisant pour 4 dashboards, et l'install Docker est triviale.
Pas de Spark / dbt
: Airflow gère lui-même les transformations SQL via
PostgresHook.run()
. Pour 8 500 commandes/jour, c'est largement suffisant.

L'API génère ses données à partir d'un

9.3 Pattern d'idempotence (obligatoire)
Pour chaque run daté
{{ ds }}
, votre transformation
staging → dwh
doit faire :
BEGIN
;
DELETE
FROM
dwh
.
fact_orders
WHERE
dt
=
'{{ ds }}'
;
INSERT
INTO
dwh
.
fact_orders
SELECT
...
FROM
staging
.
orders
WHERE
dt
=
'{{ ds }}'
;
COMMIT
;
Pourquoi
DELETE + INSERT
plutôt qu'un
MERGE
/
UPSERT
?
Parce que c'est :
Plus simple (pas de gestion de conflit ligne par ligne)
Plus performant pour des batches &gt; 1000 lignes
Plus facile à débugger (la table est dans un état connu après chaque run)
Règle absolue
: rejouer un run avec la même date = même résultat en base.
Non négociable
.

11. Découpage du projet
11.1 — Construire le pipeline ELT
L'objectif de la 1ere partie est d'avoir un
pipeline qui tourne de bout en bout
, même minimaliste. À la fin de la journée, vous devez pouvoir déclencher un DAG dans l'UI Airflow et constater que des données arrivent dans
dwh.fact_orders
.
Étapes recommandées dans l'ordre :
Démarrer le stack
(
docker compose up -d
) et vérifier que tous les services sont healthy. C'est le bon moment pour explorer l'UI Airflow et les services PostgreSQL/MinIO.
Tester l'API à la main
avec
curl
pour comprendre son format de retour. C'est plus rapide que de débugger un DAG qui appelle une API qu'on ne connaît pas.
Concevoir le modèle dimensionnel
sur papier ou Mermaid avant d'écrire du SQL. Identifier les dimensions et les faits, puis écrire le
init-db/schema.sql
. Lancez-le manuellement avec
psql
pour vérifier qu'il passe.
Implémenter le
MarketplaceAPIHook
: c'est la pierre angulaire de tout le pipeline. Encapsulez l'auth Bearer (lue depuis la
Connection
) et exposez les méthodes
get_orders
,
get_sellers
,
get_products
. Testez-le isolément via un script Python avant de l'intégrer dans un DAG.
Écrire le DAG d'ingestion étape par étape
: commencez par une seule task qui extract et imprime le résultat. Une fois que ça marche, ajoutez l'upload MinIO (via
S3Hook
), puis le load dans
staging.orders
(via
PostgresHook
). Ne sautez pas d'étape — chaque task doit être validée individuellement avant de passer à la suivante.
Implémenter la transformation
staging → dwh
avec le
pattern idempotent obligatoire
(DELETE + INSERT par partition
dt = {{ ds }}
).
Tester l'idempotence
: rejouer 3 fois le même run et vérifier que
COUNT(*)
reste identique avec
psql
. C'est la preuve que votre pipeline est fiable.
🟢
Objectif
: pipeline principal qui tourne, idempotence prouvée, données visibles dans
dwh.fact_orders
. Premier commit Git poussé.
🟠
Conseil
: ne sous-estimez pas le temps de design du modèle dimensionnel et du Hook. Bâcler ces 2 étapes au début vous coûtera 2x plus de temps en debug ensuite.
🟡
En cas de retard
: sacrifiez le 2ème DAG (refresh dimensions). Concentrez-vous sur le pipeline principal de bout en bout.

17. FAQ
Q : On peut utiliser Superset à la place de Metabase ?
R : Oui, à vos risques. Superset est plus puissant mais plus complexe. Documentez le choix dans le README. Pas de pénalité, pas de bonus.
Q : On n'a pas le temps pour les 2 dashboards Metabase, on peut skipper ?
R : Un seul dashboard avec 3 visualisations est acceptable comme MVP minimal. Mais c'est risqué — ça pèsera sur la note.
Q : Le DataQualityOperator est-il obligatoire ?
R : Non, c'est un bonus (Should). Concentrez-vous sur le MVP d'abord.
Q : On peut ajouter dbt pour les transformations ?
R : Hors scope pour 14h. Mentionnez-le dans le README comme "ce qu'on ferait avec plus de temps".
Q : Le bonus observabilité (Prometheus/Grafana) est-il vraiment réaliste en 14h ?
R : Si le MVP est fini à 14h le J2, oui : ~2h pour ajouter la stack et importer le dashboard 11010. Si vous galérez sur le MVP,
n'y allez pas
.
Q : Comment on accède à PostgreSQL DWH depuis l'extérieur du conteneur ?
R : Le port
5433
est exposé sur l'hôte. Depuis votre machine :
psql -h localhost -p 5433 -U dwh_user -d dwh
. Depuis un autre conteneur :
psql -h postgres-dwh -p 5432 ...
.
Q : Que faire si MinIO n'a pas créé le bucket ?
R : Aller dans MinIO Console (
http://localhost:9001
, login
minio_admin
/
minio_password_2026
) et créer manuellement le bucket
data-lake
. Ou exécuter
docker compose restart minio-init
.
